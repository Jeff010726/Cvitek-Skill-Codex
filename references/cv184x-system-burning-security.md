# CV184X System, Burning, And Security

Use this reference for CV184X Linux BSP, SDK compilation, rootfs, partitioning, U-Boot, boot logo, burning, secure boot, eFuse, and release hardening.

## High-Confidence Build Surface

The local CV184X manuals and repo agree on this base order:

```sh
source build/envsetup_soc.sh
defconfig cv184x
defconfig <board>
```

Then use the smallest target that matches the task:

```sh
build_kernel
build_uboot
build_osdrv
build_middleware
pack_rootfs
pack_upgrade
```

Use `build_all` only when the user needs a complete image set or the manual specifically requires a full pass. Some local-build notes say partial builds assume a prior full build; verify artifacts and dependencies before promising a partial rebuild will be enough.

Common output roots:

- `install/soc_<board>` or `install/soc_$CHIP_$BOARD`
- `install/soc_<board>/rawimages/`
- `build/output/<board>/`

- `rootfs.spinor`

## Burning And Upgrade

Relevant manuals:

- `ProductionBurningUserGuide_zh.pdf`
- `SPINANDProgrammerBurn-inUserGuide_zh.pdf`
- `CvitekBareandNon-BareProcessorBurningUpgradeOperationGuide_zh.pdf`

Common image families:

- top-level images: `fip.bin`, `boot.*`, `rootfs.*`, `system.*`, `cfg.*`
- `upgrade.zip`
- `install/soc_<board>/rawimages/*`
- signed or encrypted FIP such as `fip_enc.bin`
- SPINAND programmer FIP generated by `fip_maker`

Production burning surfaces:

- Windows USB driver: `CviUsbDownloadInstallDriver.exe`
- GUI: `cviDownloadTool`
- command-line USB: `usb_dl.exe -c cv184x -i .upgrade`
- command-line UART: `uart_dl.exe -c cv184x -p COM3 -i .upgrade`
- Linux USB example: `./usb_dl -c 184x -i <firmware path>`
- U-Boot network: `setenv ipaddr`, `setenv serverip`, `ping`, `tftpboot`
- U-Boot flash write examples: `mmc write`, `nand erase.part`, `nand write`, `sf probe`, `sf erase`, `sf write`, `cvi_sd_update`

SPINAND programmer notes:

- Use `install/soc_<board>/rawimages/*.spinand` for programmer-style raw images.
- Use `build/tools/common/spinand_tool/fip_maker` when the manual requires FIP preprocessing.
- `fip_maker` arguments depend on page size and flash ID/MID/DID. Do not invent them.
- FIP has duplication and bad-block handling rules on SPINAND. Do not write a single naive block plan without checking the flash.

Format safety rules:

- Do not mix top-level `*.spinand` images with `rawimages/*.spinand`.
- Some images carry headers; TFTP/programmer/raw flows may require different header handling.
- U-Boot `mmc write` uses block units, not byte units. Align by 512-byte blocks.
- USB burning may have power-mode requirements. Follow the manual and board documentation.

## Secure Boot And eFuse

Relevant manuals:

- `SecureBootUserGuide_zh.pdf`
- `eFuseUserGuide_zh.pdf`

FIP secure-boot concepts:

- FIP protection covers `fip.bin`; ROM/BL1 validates it.
- Key files in the manual include `rsa_hash0.pem`, `bl_priv.pem`, `loader_ek.key`, and `bl_ek.key`.
- FSBL secure boot is enabled through `CONFIG_FSBL_SECURE_BOOT_SUPPORT=y`.
- Signing/encryption tool: `python3 fsbl/plat/cvitek/cv184x/common/fipsign.py sign-enc ...`
- Output may be `fip_enc.bin`; confirm the partition image name expected by the selected burning flow.

FIT and filesystem protection:

- FIT protects kernel/FDT inside `boot.*`; U-Boot validates it.
- FIT key material is under `ramdisk/keys/`, for example `test_reeos.key`, `test_reeos.crt`, AES key, and IV.
- RootFS signing uses SquashFS signature helpers such as `append_squashfs_sig.py` and `check_rootfs_sig.sh`.
- DATA partition signing uses helpers such as `append_image_sig.py` and runtime `verify_data_sig`.

eFuse areas and APIs:

- `USER` 40 bytes
- `DEVICE_ID` 8 bytes
- `HASH0_PUBLIC` 32 bytes
- `LOADER_EK` 16 bytes
- `DEVICE_EK` 16 bytes
- `SECUREBOOT` 4 bytes
- U-Boot read: `efuser <AREA>`
- U-Boot write: `efusew <AREA> <HEX>`
- API family: `CVI_EFUSE_*`, with `cvi_efuse.h`, `libefuse.a`, and sample code in the SDK

High-risk rules:

- eFuse writes are one-way. Bits can only move from 0 to 1.
- Never suggest `efusew` as a routine step. First verify board, storage, FIP/FIT state, key material, command names, and whether the image has already been signed/encrypted.
- The manuals show both `LOCK_WRITE_*` and `LOCK_*` style names. Use live U-Boot `help`, current source, or vendor instructions for exact lock command names.
- `SECUREBOOT 01` and `SECUREBOOT 02` meanings must be checked against the current eFuse manual and boot plan before use.
- FIP and FIT are different protection layers. Do not claim one replaces the other.

## Cybersecurity Hardening

Relevant manual: `CyberSecurityPrecautionsforSDKSecondaryDevelopment_zh.pdf`.

Common hardening points:

- Disable U-Boot boot interruption in release images, for example by setting `CONFIG_BOOTDELAY=-2` when appropriate.
- Remove or disable risky U-Boot command families such as memory access commands if the product threat model requires it.
- Harden root login by editing the board rootfs overlay, then repack rootfs.
- Disable unused Linux UART nodes in board DTS and rebuild the kernel.
- Mount removable media with restrictive options such as `noexec` when applicable.
- Disable or physically protect JTAG and bare-burning paths for production.

Avoid:

- Do not apply hardening changes blindly to development boards where serial recovery is still needed.
- Do not edit generated rootfs output and forget to update the source overlay or packaging flow.
- Do not claim a software config alone fully protects physical debug interfaces.
